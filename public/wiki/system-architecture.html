System Architecture

Last updated: November 10, 2025 | Owner: Sarah Chen, Lead Control Systems Engineer | Version: 3.2
📋 Document Purpose: This document describes the complete control system architecture for Project Nexus, including PLC configuration, communication protocols, and system integration.

Overview

Project Nexus utilizes a distributed three-PLC architecture designed for high reliability, modularity, and safety compliance. The system separates critical safety functions from operational control and show effects, allowing independent operation and maintenance of each subsystem.

Architecture Philosophy

The design follows industry best practices for theme park attractions:

  • Separation of Concerns: Safety, control, and effects are isolated into separate PLCs
  • Defense in Depth: Multiple layers of safety interlocks and redundancy
  • Fail-Safe Design: System defaults to safe state on any failure
  • Modularity: Each PLC can be serviced independently without full shutdown
  • Scalability: Architecture supports future expansion and upgrades

PLC Specifications

Main Control PLC (Port 502)

Parameter Specification
Model OpenPLC Runtime on Industrial PC
Purpose Primary ride control and coordination
Functions • State machine control
• Vehicle position tracking
• Speed management
• Zone control logic
• Show sequence timing
I/O Count 33 Coils (Digital Outputs), 10 Registers (Analog I/O)
Scan Time ~10ms typical
Communication Modbus TCP (Primary), Handshake with Safety & Effects

Safety PLC (Port 503)

Parameter Specification
Model OpenPLC Runtime (Safety-rated configuration)
Purpose Safety-critical monitoring and interlocks
Functions • Emergency stop monitoring
• Safety gate interlocks
• Zone occupancy detection
• Ride event validation
• Fault detection
I/O Count 16 Safety Inputs/Outputs
Scan Time ~5ms (prioritized for safety response)

Effects PLC (Port 504)

Parameter Specification
Model OpenPLC Runtime with Show Control Extensions

• Audio triggering
• Special effects (smoke, water, wind)
• Projection mapping sync
• Pyrotechnics (when approved)

Communication Architecture

Modbus TCP Protocol

All three PLCs communicate via Modbus TCP over Ethernet. The protocol provides:

  • Standard industrial protocol with wide tooling support
  • Deterministic timing for real-time control
  • Simple troubleshooting with standard Modbus tools
  • Low latency (typically <10ms round-trip)

Address Mapping

Address Range Type Purpose
0-32 Coils (R/W) Digital control signals (enable, commands, status)
0-9 Holding Registers (R/W) Analog values (position, speed, counters)
0-9 Input Registers (RO) Read-only system data (sensors, diagnostics)

Inter-PLC Communication

The three PLCs exchange status and coordination signals via dedicated Modbus coils:

  • Coil 31: Safety PLC Ready - Heartbeat from Safety to Main
  • Coil 32: Effects PLC Ready - Heartbeat from Effects to Main
  • Coils 8-16: Event Enable signals from Main to Safety
  • Coils 17-25: Event Active feedback from Safety to Main
⚠️ Critical Design Rule: The Main PLC will not start the ride unless both Safety PLC Ready (Coil 31) and Effects PLC Ready (Coil 32) are TRUE. This ensures all systems are online before operation.

Network Topology

All PLCs connect to a dedicated industrial Ethernet switch with the following requirements:

  • Managed switch with VLAN support
  • Quality of Service (QoS) configured for PLC traffic priority
  • Redundant power supplies
  • DIN-rail mounting for control cabinet installation
  • Isolated from guest Wi-Fi and corporate networks

HMI Integration

The HMI/SCADA system connects to all three PLCs simultaneously via:

  • Protocol: WebSocket server providing real-time bidirectional communication
  • Port: 8765 for WebSocket connections
  • Data Flow: HMI sends commands via Modbus writes, receives status updates via Modbus reads
  • Update Rate: 100ms (10Hz) for smooth visualization

Reliability & Redundancy

System reliability features include:

  • Watchdog Timers: Each PLC monitors heartbeat signals from others
  • Fail-Safe Outputs: All critical outputs default to safe state on PLC failure
  • Network Redundancy: Dual Ethernet paths available for critical signals
  • UPS Backup: 30-minute battery backup for graceful shutdown
  • Hot Spare PLCs: Available for rapid replacement if needed
